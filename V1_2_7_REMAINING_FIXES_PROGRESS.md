# v1.2.7 Remaining Financial Fixes — implementation progress

Tracking doc for `ManageMyFinance_v1.2.7_Remaining_Financial_Fixes.md` — a follow-up audit found real remaining issues after the first remediation pass (tracked in `FINANCIAL_CORRECTNESS_PROGRESS.md`). User chose "all 5 phases + cleanup tasks, sequentially" when asked how to scope this, including the historical-FX system and debt-posting schema that were deliberately deferred in the first pass.

## Phase 1 — Investment snapshot valuation (P0) — DONE
Fixes: FIN-001 residual (pre-snapshot position sold post-snapshot double-counts historical-cost gain/loss the snapshot already captured)
- [x] Verified the bug is real by hand-trace before touching code: buy 10@€100, snapshot=€1,500, sell all 10 for €1,500 → old code computed €2,000 (double-counted the €500 the snapshot already reflected), not the correct €1,500
- [x] New `pureCashAsOf()` — snapshot-blind raw cash, used only to back out the known-cash portion of a snapshot's total so the remainder can be attributed to securities
- [x] New `investmentBucketsForValuation()` — a mark-to-market reset at the most recent applicable snapshot: every currently-held ticker's cost basis is rescaled so the total reconciles with the snapshot's actual value, then ordinary moving-average accounting continues from that baseline for transactions after the snapshot. MVP simplification documented: with multiple snapshots, only the most recent one resets (no chained resets).
- [x] `investingTotalValueAsOf()` now uses the reset-aware bucket set for its realized-P/L-since-anchor term when a snapshot exists, instead of plain historical-cost realized P/L
- [x] Historical-cost `investingHoldings()`/`investingRealizedPnLAsOf()`/`investmentStateAsOf().realizedPnL` deliberately left untouched — these report the user's true all-time cost basis and realized gain "for their own record," per the doc's explicit requirement to keep that separate from valuation
- [x] Implemented the doc's Test A/B/C/D/E: added 4 new tests (D and E were already covered by existing regression tests from the first pass) — all 4 new tests verified to genuinely fail against the pre-fix code (via `git stash`) with exactly the predicted wrong values before passing with the fix
- [x] `npm run typecheck` clean, full suite green: 52 files / 1180 tests

## Phase 3 — Complete FX correctness (P1) — DONE
Fixes: FIN-008 residual (historical flows still use today's rate table; missing rate still silently converts 1:1)
- [x] `currency.ts` — `FxContext.history?: FxHistory` (dated rate table, `Record<date, ExchangeRates>`); `convert()` gains an optional `date` parameter
- [x] **Flow vs stock split**: `kpi.ts`'s `amountIn()` (transactions) now converts at `tx.date`; `accountAmountIn()` gained an optional `date` param, passed as `snapshot.date` from `signedSnapshotBalance` (a snapshot is a dated observation) but omitted from `signedOpeningBalance` (no date of its own, always current). Same treatment applied to the other direct `convert()` call sites: `reports/query.ts` (report rows), `strategy.ts` (`essentialMonthlyAverage`), `transfers.ts` (transfer-pair matching), `modals/CategoryDrilldownModal.ts`. Left deliberately undated (current/stock semantics, correctly unchanged): `subscriptions.ts`'s `toBaseCurrency` (a recurring current cost, not a dated flow) and `InvestingDashboard.ts`'s live price-quote conversion.
- [x] **Missing-rate contract**: `convert()` now returns `NaN` (not a plausible 1:1 passthrough) when neither a historical nor a current rate can be resolved — chose this over a `ConversionResult`-style return-type rewrite specifically to avoid a signature change cascading through the ~40+ call sites of `amountIn`/`accountAmountIn` inside kpi.ts alone. `money.ts`'s `formatMoney()` (the single money formatter every screen goes through) and `ui/metricsTable.ts`'s `formatPct()` both render NaN as "Incomplete" instead of silently defaulting to 0/"NaN%" — this makes the sentinel visible everywhere for free, since NaN propagates through any sum it's part of.
- [x] **Deliberate design choice, documented in code**: when a `date` is given but no historical rate has been backfilled for it yet, `convert()` falls back to the *current* rate table (matching the pre-existing, long-standing behavior) rather than immediately reading as incomplete. Only a currency with no rate anywhere — current or historical — returns NaN. Rationale: a real multi-year vault could have hundreds of distinct historical dates, and marking all of it "Incomplete" the moment this feature ships, before any backfill has run, would be a worse regression than the approximation it replaces. Once a date is backfilled, the historical rate is used preferentially and is then stable regardless of later current-rate changes (satisfies the doc's "historical stability" test).
- [x] `fx.ts` — new `fetchHistoricalRates(date)`, same Frankfurter/ECB source and inversion logic as the existing `fetchLatestRates`, one request per date
- [x] Persistence: new `FinanceSettings.exchangeRateHistory` (shared across portfolios, same as `exchangeRates`), wired into `FinanceStore.fx`
- [x] Settings UI: new "Backfill historical rates" action in Settings → Currency — finds every distinct date a non-base-currency transaction or snapshot falls on, fetches whatever isn't already cached, shows progress, reports partial failures as retryable
- [x] Base-currency change: no new code needed — transaction amounts were already never mutated (confirmed structurally), and the pivot-through-EUR formula in `convert()` already produces the right number for a new base currency using whichever rate table (historical or current) applies; added an explicit test proving the pivot math at a historical date with a non-EUR base
- [x] Implemented the doc's required tests: historical stability, current stock revaluation, historical snapshot (end-to-end through `netWorthAsOf`, not just at the `convert()` unit level), missing rate, base-currency-change pivot
- [x] Also fixed while in this area (overlaps Phase 5.4): Settings' stale "the only network request this plugin ever makes" claim (price refreshes also contact Yahoo Finance/CoinGecko) and the "counted one-for-one" wording (now reads "Incomplete", matching the new NaN behavior)
- [x] `npm run typecheck` clean, `npm run build` succeeds, full suite green: 52 files / 1198 tests
- **Known follow-up, not fixed**: `InvestingDashboard.ts`'s live price-refresh flow doesn't distinguish "couldn't fetch a price" from "fetched a price but the quote's currency has no rate" — a NaN could reach the balance-snapshot prefill in the latter case. Minor, pre-existing-shaped edge case, not a core Phase 3 requirement.

## Phase 4 — Debt principal/interest/fee splitting (P1) — DONE
Fixes: FIN-012 residual (transaction schema can't represent a payment containing both principal and interest, e.g. a mortgage payment)
- [x] Chose the "acceptable MVP alternative" from the doc, not the full posting-array architecture: `Transaction.principalAmount?/interestAmount?/feeAmount?` (all in the transaction's own currency), added to `types.ts`, `store.ts`'s `TX_COLUMNS`/`NUMERIC_COLUMNS` (append-only, per the existing schema-migration convention)
- [x] **Real producer**: new conditional "debt payment split" section in `modals/TransactionEditModal.ts`, shown only when the selected account is debt-carrying and the direction is a credit — exactly the case the classifier reads these fields for. Live remainder hint ("€X of €Y split out"), non-blocking. Clears the fields on save if the account/direction no longer applies, rather than leaving stale data behind.
- [x] **Real consumer**: `finance/semantics.ts`'s classifier gained a new rule (checked ahead of both the refund rule and the bare debt-principal rule): a debt-carrying account's credit with `interestAmount`/`feeAmount` set classifies as `debt-principal` with `affectsExpense = interest + fee`, confidence `"explicit"` — only the real cost counts as expense, the rest stays the balance-sheet movement it always was. A bare (unsplit) payment is completely unaffected — same as before Phase 4.
- [x] **Found and fixed a deeper bug while wiring this in**: every consumer of `affectsExpense`/`affectsIncome` (`applyClassified` in `summarizeByYear`/`summarizeByMonth`, `categoryTotals`, `primaryCategoryTotals`, `primaryCategoryIncomeTotals`, `fiExpenseBase`) assumed those fields always equal ±the transaction's full amount — true for every kind that existed before Phase 4 (by construction, not by any check), but false for a split payment where `affectsExpense` is only a fraction of `tx.amount`. Fixed all of them together with one new shared helper (`scaledEconomicAmount`) that scales proportionally against `tx.amount` instead of substituting the full converted amount — verified to reproduce the exact old behavior for every pre-existing kind (0 test regressions) while correctly handling the new split case.
- [x] `kpi.ts`'s `debtPrincipal` bucket (used by `CreditDashboard.ts`'s "Paid off") also had to move: it used to accumulate only inside the fully-economically-neutral branch, which a split payment no longer is (its interest portion isn't neutral) — moved to accumulate unconditionally whenever `kind === "debt-principal"`, using a new `debtPrincipalPortion()` helper that reads the actual principal slice, not the full payment, when a split is present
- [x] Implemented the doc's required tests at both the classifier level (`semantics.test.ts`) and the full `summarizeByYear`/`categoryTotals` pipeline level (`kpi.test.ts`): mortgage split, loan with fee, unsplit credit-card payment (proving zero regression), an explicit split overriding a category-based refund guess, and split fields being ignored on a non-debt account
- [x] `npm run typecheck` clean, `npm run build` succeeds, full suite green: 52 files / 1207 tests
- **Deliberately not done**: no new "Interest paid" row added to `CreditDashboard.ts` — the existing "Paid off"/"Charged"/"Net" rows already read correctly from the now-split-aware `debtPrincipal`/`expenses` fields, satisfying the doc's exit criterion ("debt dashboards consume principal/interest semantics") without needing a new UI element or a new YearSummary field to separate "interest" from "ordinary purchases" within `expenses`.
