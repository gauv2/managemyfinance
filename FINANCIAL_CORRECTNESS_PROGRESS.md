## Phase D — FI model + FX model — DONE (FX scoped down, by explicit user decision)
Fixes: FIN-011, FIN-008
- [x] `fiProjection()` effective monthly return: `Math.pow(1 + annualReturn, 1/12) - 1`, replacing `annualReturn / 12`
- [x] New `fiExpenseBase()` in kpi.ts: trailing 12 complete calendar months of expenses (annualized), or however many complete months exist if there's under a year of history — `{ annual, monthsCovered, complete }`. Wired into `DashboardSection.ts`'s FI meter, replacing the old "whichever calendar year the range touches" basis, which used the still-in-progress current year's partial total as if it were a full year on every day but Dec 31st. The "monthly contribution" figure feeding `fiProjection()` got the equivalent fix (divided by months actually elapsed this year, not a flat 12).
- [x] Settings label: "Expected annual return" → "Expected real annual return", with description clarifying real = after inflation, and an explanatory note on why (the FI target is stated in today's money, so a nominal return would overstate progress). - [x] `currency.ts`'s FIN-008 — **scoped down by explicit user decision** (asked via AskUserQuestion after determining the full fix needs new network fetching + a persisted rate-history cache + touching ~9 files' conversion call sites): implemented the "make missing-rate cases visible" half only, not historical/dated rates or the base-currency-recompute pivot.

## Phase E — Debt splitting + label rename — DONE (schema fields deliberately deferred)
Fixes: FIN-012, FIN-013
- [x] New `YearSummary.debtPrincipal` field in `kpi.ts`'s `summarizeByYear`/`summarizeTotal`: debt-principal payments (the classifier's `debt-principal` kind, from Phase A) tracked as their own bucket instead of being invisible inside `transferAmount`. Necessary because Phase A's classifier fix already made a card payment correctly *not* count as `income` — which is right, but left `CreditDashboard.ts`'s "Paid off" row (which read `y.income`) silently showing €0 for every year, a new-looking regression that's actually the old bug (payment counted as generic income) being replaced by a different gap (payment counted as nothing) rather than the real fix (payment counted as what it is: principal).
- [x] `CreditDashboard.ts` — "Paid off" now reads `debtPrincipal`; "Net" redefined as `debtPrincipal − expenses` (paid down minus newly charged) instead of the old `income − expenses` (always ≈ `−expenses`, since income is now correctly ~0 for a credit account); the "Savings rate" row is removed outright rather than left showing "N/A" every single row — a credit account has no income for the concept to apply to at all, so a permanently-empty row is clutter, not a reading
- [x] Renamed "Personal inflation rate" → "Spending change" in `DashboardSection.ts` (history table's delta row + the year-over-year chart series) — the old name claimed a rigor (a real inflation measure, basket-of-goods style) this number never had; it's the plain YoY change in recorded spending. Matching wording fix in a `transfers.ts` doc comment that referenced the old name.
- [ ] **Deliberately not added**: `Transaction.principalAmount`/`interestAmount`/`feeAmount` optional fields. Nothing in the current import pipeline or UI can populate a real principal/interest split for a single payment row — no bank/loan statement parser breaks a payment down that way today. Adding unused optional fields now would be speculative schema plumbing with no producer or consumer, not a fix for an observable bug: the actual user-visible FIN-012 problems (a payment misread as income, a meaningless savings-rate row) are already fixed above via the classifier's account-level `debt-principal` kind, which doesn't need a per-transaction split to work. Revisit if/when an import source (e.g. a mortgage/loan statement) actually reports the two separately.

## Verification
- [x] typecheck + full test suite green after every phase (running total after the Phase A/B review fixes below: 51 files / 1151 tests)
- [x] Independent review agent after Phase B (P0 boundary), against FIN-001–006 acceptance tests read directly from the PDF. Verdict: FIN-002/003/004 satisfied as implemented; FIN-006 correctly still open (not started); **two real regressions found and fixed**:
  1. **FIN-001 snapshot+post-trade bug**: the original fallback only added open cost basis back when *no* snapshot existed at all — once any snapshot was recorded, trades dated after it went back to draining net worth by their full raw cash amount (reviewer traced a concrete case: snapshot €20,000, buy €2,000 → net worth read €18,000, the literal bug FIN-001 was supposed to fix). Fixed by replacing the "only when no snapshot" gate with `investingTotalValueAsOf()` — an anchor (snapshot or opening balance) plus non-trade cash since that anchor plus realized P/L since that anchor — which is algebraically the same formula in the no-snapshot case and additionally correct in the with-snapshot-plus-later-trades case. Locked in with new regression tests in `kpi.test.ts` (buy-after-snapshot stays neutral, sell-after-snapshot realizes only the gain, dividend-after-snapshot still counts as real cash).
  2. **FIN-005/012-groundwork priority bug**: `classifyTransaction`'s debt-principal rule was checked *before* the refund rule, so a merchant refund credited back onto a credit card was absorbed as economically-neutral debt-principal instead of netting against the original expense category — silently overstating that category's spend. Fixed by swapping the rule order (refund check now runs first); a bare/uncategorized credit-card credit still correctly falls through to debt-principal. New tests in `semantics.test.ts`.
  - Also independently found and fixed while investigating: `investmentBucketsAsOf` processed transactions in `store.transactions` array order with no chronological sort, but moving-average cost basis is order-dependent (a sell's pre-sale average cost is only meaningful relative to buys that actually preceded it) and nothing guarantees the array is date-ordered. Fixed by sorting the filtered buy/sell list by date before processing; regression test added (sell listed before its buy in the array still computes correctly).
  - `investmentStateAsOf` (not yet wired into any consumer) was also updated to use the same `investingTotalValueAsOf()` formula for `totalValue`, so it can no longer disagree with `netWorthAsOf` on the same account.
